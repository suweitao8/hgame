# HGame 引擎评分机制（v5.1 · 纯设计与能力驱动 · 四引擎 Web 绝对评分）

**客观结论（2026-11-22 · v5.1 口径）**：在移除“真机移动端实证”与“商业上线作品”等外部运营指标、纯以**架构设计与运行时技术能力**作为唯一评分依据后，四大引擎在 Web/HTML5 绝对 0–100 能力体系下的真实排序为 **Unity 6.x URP Web（`80.0 / 100`） > HGame 1.0.0（`78.0 / 100`） > Cocos Creator 3.8 Web（`71.3 / 100`） > Godot 4.3+ Web Compatibility（`64.6 / 100`）**。HGame 当前与 Unity Web 仅差 **`-2.0` 分**，主要受限于 `A2` 全管线 RenderGraph 默认未接管主光栅、`P2` WebGPU Compute 剔除默认未接入主适配器、`R2` 缺离线 Lightmap/AO 烘焙、`P1` Rapier 物理仍在主线程、`S2` 缺跨骨架动画重定向、`A3` 缺远程分包加载器及 `R3` 缺声明式材质变体 DSL。

---

## v5.1 评分口径与定位

1. **只评设计与运行时技术能力（Web/HTML5 端）**：严格评估浏览器/小游戏宿主可落地的四大对象：`HGame 1.0.0`、`Unity 6.x URP Web`、`Cocos Creator 3.8 Web`、`Godot 4.3+ Web (Compatibility)`，移除无官方 Web 导出能力的 Unreal。
2. **绝对 0–10 分制与固定底座权重**：17 项细分能力全部按绝对 0–10 分（步长 `0.5`）独立打分，沿用固定底座权重：**架构与资产 `18`、图形渲染 `30`、性能与硬件 `24`、核心运行时子系统 `20`、多人与确定性网络 `8`**（合计 `100` 分）。
3. **取消“Unity = 100.0”归一化**：任何引擎能力满分均为 `100.0`，禁止通过相对比值构造“超 100”分数；`对 Unity 比值` 仅作横向倍率参考展示。
4. **聚焦纯技术底座**：编辑器 GUI、社区生态、商业上线数量及移动端真机运营矩阵**不计入评分**，所有分数完全取决于引擎设计完备度、默认主路径接线情况与工业级能力清单满足度。
5. **单一数据真相源**：全部原始分、能力成熟度等级、工业级清单（`industrialChecklist`）、竞品依据与实测包体数据存放在 [engine-scorecard.json](scorecard/engine-scorecard.json)，本文档中的总表与逐项表均由 `node scripts/score-engines.mjs --write` 自动渲染。

## v5.1 评分防虚高六大铁律（Hard Caps）

1. **未接默认管线封顶 `<= 7 分`**：能力仅在独立 Helper 中，未进入 `Application` / `createThreeAdapter` / `createPostPipeline3D` / 默认 Profile 主路径（`defaultPath: false`），最高 `7 / 10`。
2. **仅 Node Mock 缺复杂场景/真 GPU 实证封顶 `<= 7 分`**：未经过复杂负载（千级实例/曲面接缝/真 WebGL2/WebGPU/Web Audio）验证，按能力等级 `C1` 封顶 `7 / 10`。
3. **关键工业特性缺失封顶**：缺核心能力（如未进默认 RenderGraph、缺 Lightmap/AO 烘焙、缺物理 Worker 化或动画重定向）不可按工业级满分给分。
4. **“空壳挂载 / 假异步 / 无真实信号输入”零加分铁律**：创建了节点但无上游输入（如 `ConvolverNode` 没有 Voice Send）、`stepAsync` 仍主线程跑完算法、只触发距离回调但未切换实际纹理资源等情形，**按未实现计分，严禁加分**。
5. **能力成熟度与工业清单双封顶（`C0–C4`）**：HGame 单项得分必须同时满足 `score <= capabilityCap` 且 `score <= maxAllowed`，其中 `maxAllowed = defaultPath ? (8 + 2 × met / total) : 7`（`met/total` 为该项 `industrialChecklist` 满足比例）；同时 `C4` 要求清单全部满足（`met == total`），`C3` 要求至少满足 1 条（`met >= 1`）：

| 能力等级 | 工程与设计判定要求 | 单项得分上限 |
| :---: | --- | ---: |
| `C0` | 仅设计 / 文档声明，无可执行验证 | **5.0** |
| `C1` | 具备完整 API 与 Node 单元测试 | **7.0** |
| `C2` | 默认主路径接线 + 浏览器真 GPU 实测通过 | **8.0** |
| `C3` | 满足 `C2` + 工业级清单（`industrialChecklist`）部分满足（`met >= 1`） | **9.0** |
| `C4` | 工业级清单全部满足（`met == total`）且默认接线并经过浏览器真 GPU 实测 | **10.0** |

6. **竞品依公开边界 + 实证路径强校验 + 防漂移门禁**：竞品分数必须基于官方公开能力边界并填写 `competitorNotes`；HGame 每项 `proofFiles` 必须指向已被 Git 跟踪的运行时源文件（浏览器基准脚本记入 `benchmarkFiles` 作为证据）；防漂移门禁以 `node scripts/score-engines.mjs --check`（已跟踪）为准，辅以仓库测试 `tests/engine-scorecard.test.mjs`拦截任何手改表格或越界打分行为。

## 0–10 分档说明与 17 项逐项判定细则

### 0–10 分分档说明

| 分数 | 工程含义 |
| ---: | --- |
| 0–2 | 缺失，或仅停留在原型片段，尚未接通主运行入口。 |
| 3–4 | 具备基础 API，但仅覆盖单一窄路径，常规游戏必须大量手写胶水代码。 |
| 5–6 | **可用级**：核心能力已跑通主路径并有单元测试，但缺少进阶生产特性或仅覆盖部分子场景。 |
| 7–8 | **生产可用级**：进阶能力完善且默认主路径对齐；受“未默认接线”或部分工业级清单项未满足约束。 |
| 9–10 | **商业工业级**：默认主路径全链路打通、工业级清单（`industrialChecklist`）高度或全部满足，并在浏览器真 GPU 环境经过实证。 |

## 3. 竞品 Web 端真实能力边界与包体对比（修正后）

### 竞品 Web 端能力边界核实

- **Unity 6.x URP Web（`80.0 / 100`）**：Unity 6 URP 拥有全管线 Render Graph、成熟的光照贴图烘焙、APV 探针、DBuffer 贴花、Mecanim 人形重定向与远程 Profiler，是通用 Web 管线的标杆；但在 Web 平台存在明确硬边界——**Unity WebGL 官方不支持 AudioMixer DSP 效果与音频滤镜**（仅保留基础播放与音量控制，故 `S3 = 5.0`）；此外 `STP` 等 Compute 上采样在 WebGL2 上不可用，C# 主运行默认为单线程（开启多线程需强依赖 COOP/COEP 隔离头）。
- **Cocos Creator 3.8 Web（`71.3 / 100`）**：2D 合批/UI/Spine/Widget、CRP 自定义渲染管线、Lightmap 烘焙、AssetBundle 与分包能力完整；短板在于缺乏内置确定性锁步物理与状态回滚网络框架（`N1 = 3.5`）、默认 Web Audio 缺乏多段参数 EQ 与卷积混响链路，以及超大规模 `Bone-VAT` 群体与 WebGPU 计算管线特化度较弱。
- **Godot 4.3+ Web（`64.6 / 100`）**：2D 节点、UI Control 布局与场景文本化设计极具优势，且 **Godot 4.3 新增了单线程 Web 导出（不再强制依赖 `SharedArrayBuffer` 与 COOP/COEP 宿主头）**；然而其 Web 端被迫锁定在 **Compatibility/GLES3 后端**（丢失桌面端 Forward+、SDFGI、SSR、TAA、3D Decal 与 Compute 剔除），不支持 C# Web 导出，且 4.3 单线程 Web 默认走 Sample 播放路径会导致总线 DSP 效果丢失、首次 Shader 编译易卡顿。

## 4. HGame 当前技术与设计不足（按影响排序）

1. **关键能力仍停留在独立 Helper，未接管默认主路径（`A2 = 7.0`, `P2 = 7.0`）**：`compileRenderGraph` 目前仅调度后处理而非 Three 主光栅，`gpuIndirect` 在 `createThreeAdapter` 中默认为 `false` 且参数名与 `createGpuIndirectCuller3D` 存在不一致风险，形成“能力存在但默认业务路径吃不到”的架构割裂。
2. **缺少内置 Lightmap UV2 展开与 GPU 光照/AO 烘焙管线（`R2 = 7.5`）**：仅有运行时 `applyBakedLightmap3D` 挂载点，缺乏自动 UV2 展开与增量式渐进烘焙器，3D 场景被迫较多依赖实时多灯与屏幕空间计算。
3. **Rapier 物理与骨骼姿态计算仍在主线程（`P1 = 7.0`）**：仅流场与 NavMesh 寻路进入 `worker-sim.js`；高密度刚体碰撞在单核上仍直接挤占主线程帧预算。
4. **资产压缩与分包流送缺远程 Bundle 与内置 BasisU 编码器（`A3 = 8.0`）**：运行时支持 KTX2 解析与 50MB 审计，但缺少内置 BasisU 编码器（依赖外部 `toktx`），且缺少按需加载/卸载与断点重试的远程分包加载器。
5. **动画与 2D 商业资产兼容能力不足（`S2 = 7.5`, `R1 = 8.0`）**：缺少跨骨架骨骼动画重定向（Retargeting）与 Spine / DragonBones 运行时支持。
6. **材质系统缺少声明式多变体 Keyword DSL（`R3 = 7.5`）**：`material-graph3d.js` 偏单次注入，缺少类似 Shader Graph / Effect 的声明式 Keyword 变体字典与 `customProgramCacheKey` 复用机制。
7. **过往包体与评分口径曾存在误导**：v4 的“`< 1 MB` 核心 ESM”忽略了 `Three + Rapier3D` 合计 `2.41 MB gzip` 的真实传输下限，且用相对 Unity 归一化掩盖了上述技术缺口。
